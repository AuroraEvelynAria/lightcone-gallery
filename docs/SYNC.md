# 双端数据同步（设计稿）

> 目标：**手机和电脑互通数据**。一端补过的元数据，另一端直接用；收藏、评分、标签图库同理。
>
> 参考对象是 **Resilio Sync** 的模型（纯 P2P、共享密钥即权限、局域网直连、不经过云）。
> 本文只写「怎么实现」，不写代码。

## 一、要抄 Resilio 的哪几条

先分清哪些是核实的、哪些是通行做法：

**已核实**（维基百科 Resilio Sync 条目）：

- **纯 P2P，没有云**：文件在自己设备之间直接走，官方服务器不存
- 同步范围是「局域网内，或经修改版 BitTorrent 协议跨网」
- **权限靠一个「secret」分发**，**加密密钥由它派生**（AES-128 计数器模式）
- **直连优先**；目标不可达（比如在防火墙后）才经中转节点
- 多设备组成网状

**通行做法**（P2P 同步工具普遍这么干，Resilio 大概率也是）：局域网内靠 **UDP 广播**互相发现、固定端口。

**要抄的三条**：

| 抄 | 为什么 |
| --- | --- |
| **一个共享密钥搞定配对** | 不用输 IP、不用另发 token —— 密钥同时是「凭据 + 鉴权 + 加密材料」 |
| **局域网自动发现** | 打开应用就找到对方，这才有「和 Resilio 一样」的手感 |
| **直连传输，不经服务器** | 隐私上干净，而且根本没有服务器要维护 |

**不抄的两条**（都是为「几 TB 文件」设计的，我们用不上）：

- 中转 / NAT 打洞 —— 跨网建议交给 Tailscale，见第六节
- 分块哈希树（Merkle）增量 —— 我们的载荷小三个数量级，见下一节

## 二、为什么这个项目特别适合抄这套

量的都是真实数据（本机电脑库，2026-10-13）：

| 数据 | 行数 | JSON |
| --- | --- | --- |
| 元数据 | 3134 | 0.37 MB |
| 官方标签 | 24005 | 0.74 MB |
| 收藏 + 评分 | 38 | 1 KB |
| **合计** | | **约 1.1 MB**（gzip 后约 300KB） |

三个性质让同步逻辑能做得极简：

1. **载荷小**：1.1MB，局域网一秒内。所以**每次全量传，不做增量、不做断点续传**。
   这一条砍掉的是整套最容易出 bug 的东西（版本向量、变更日志、乱序重放）。
2. **键是 pid**：`images.pid` 覆盖率 **4435/4496 = 98.6%**；`artworks` / `illust_meta` /
   `illust_tags` 的 pid 都是现成的键。两端的**文件路径完全不同**（`D:\pixez pics\…`
   vs `/storage/emulated/0/Pictures/pixez/…`），但 pid 是同一个。
3. **元数据是「写一次、之后只读」**：一条 pid 抓成功之后基本不会再变，
   所以合并规则简单到「取新的那份」就够。

## 三、协议设计

### 3.1 身份：一个同步密钥

- 电脑端生成 32 字节随机数 → base32 成 26 个字符（字母表去掉 `0O1IL` 这些易混字符），
  显示成 `LC7K-3F9Q-M2XR-8WTB-VHN4-PS6D`
- 手机端**输一次**（或扫电脑上的二维码）
- 这一个密钥兼任三件事：**配对凭据 + 请求鉴权（`Authorization: Bearer`）+ 载荷加密的密钥材料**

> 抄 Resilio 的地方就在这：没有「账号」、没有「服务端下发 token」，
> 一串字符写完，两台设备就互认了。

### 3.2 发现：局域网 UDP 广播

```
每个设备：UDP 17890 上既广播也监听
  广播 → 255.255.255.255:17890 与 <子网广播>:17890
  报文 → {"magic":"LCGS","v":1,"key":<sha256(secret) 前 8 字节>,"device":"phone","port":17891}
  收到 key 一样的 → 从 recvfrom 拿到对方 IP，回一个同样的包
```

- 双方各自记下对方的 `IP:port`，30 秒有效；过期就再广播一次
- **不做 mDNS**：Android 10+ 对组播限制多，而且多数家用路由器默认开 AP 隔离 —— 两者都受限时广播至少更简单
- 拿不到广播结果就**退回手填** `IP:端口`（第一节说的「配对一次」）

### 3.3 传输：一次请求搞定双向

```
POST /v1/sync            Authorization: Bearer <secret>
{
  "device": "phone-2f9c",
  "sent_at": 1760000000,
  "meta":     [ {pid, title, artist_uid, artist_name, page_count, x_restrict,
                 sanity_level, illust_type, create_date, fetched_at, error, missing}, … ],
  "tags":     [ [pid, tag], … ],
  "artists":  [ {uid, name}, … ],
  "opinions": [ {pid, favorite, rating, updated_at}, … ],
  "galleries":[ {name, tags, rating}, … ]
}

→ 200 同样的结构：**服务端有、而客户端缺或落后的那些**
```

- **一次往返**：客户端把自己的全量推上去，服务端合并后，把「你缺的 / 你旧的」回给客户端
- 客户端拿到响应后按**同一套规则**在本地再合并一次
- 没有会话、没有断点、失败重来一遍就行 —— 这是「载荷小」换来的最大红利

### 3.4 合并规则（这块是核心）

| 数据 | 规则 |
| --- | --- |
| **元数据** | 先看状态优先级：**成功 > Pixiv 已删除 > 抓取失败**；同级才比 `fetched_at`，大者赢 |
| **标签** | 按 pid **整组替换**（标签是作品的属性，不会各自演化出冲突） |
| **画师名** | 名字 ≠ uid 的那个优先（uid 是回退值，等于 uid 说明没抓到真名）；两个都是真名时保留服务端的 |
| **收藏 / 评分** | 比 `opinion_updated_at`，大者赢（需要新加这一列） |
| **标签图库** | 按名字；名字撞了以服务端为准（它只有标签 + 分级，天然可移植） |
| **「从作品库移除」** | `ignored_artworks` 的键是 `(pid, page)`，也可移植 —— 手机上移除的，电脑重扫不再收回来 |

> **元数据那条必须按状态优先级，不能只看谁新。** 否则手机上一次网络超时，
> 就会把电脑上好好的一条冲掉 —— 这是最容易被忽略、又最气人的一种「同步事故」。

### 3.5 冲突判定与时钟

「后来者赢」靠的是 `opinion_updated_at`。两台设备都跟着 NTP，实测偏差通常在 1 秒内，
但不是零。所以：

- 时间戳记到**秒**
- 同秒冲突时**按 `device_id` 字典序定序**（两边算出同一个赢家，结果一致）
- 这样即使两台机器差几秒，也不会出现「A 说它赢、B 也说它赢」

### 3.6 安全

- 密钥是唯一的凭据，**只绑局域网网卡**，绝不监听 `0.0.0.0` 之外的接口、**不做端口映射 / UPnP 打洞**
- 载荷用 `secret` 派生的密钥做 **ChaCha20-Poly1305** 加密（rustls 已在依赖树里，但自己加一层对称加密更省事）
  —— 元数据里有 R-18 标记和标题，不能在同一个 Wi-Fi 下裸奔
- **第一次监听端口时 Windows 防火墙会弹窗**，界面上要提前说一句，否则主人会以为同步坏了

### 3.7 不传什么

| 东西 | 为什么不传 |
| --- | --- |
| 缩略图 | 几百 MB，而且哪边都能重新生成 |
| 原图 | 硬约束：应用对图库目录**只读不写**，同步不该例外 |
| 图库路径 / 相册 | 路径是本机的东西（`D:\pixez pics` vs `/storage/emulated/0/...`），同步没有意义 |
| 外观 / 代理设置 | 各设备本来就该不一样（电脑用 DWM 材质、手机的代理地址不同） |

## 四、要改哪些东西

**schema**（三处，都不大）：

```sql
ALTER TABLE images ADD COLUMN opinion_updated_at INTEGER;   -- 收藏/评分的最后修改时间
CREATE TABLE sync_peers (id, name, url, token, last_synced_at, last_result);
CREATE TABLE sync_meta  (key, value);                        -- 本机 device_id、secret 等
```

**后端**：三件事

1. 一个小 HTTP 服务（只绑局域网，两三个端点）
2. 合并逻辑（上面那张表）—— **必须能脱离网络单测**，这是整个功能最该被测的部分
3. 「导出同步状态」的统计（给界面显示「上次同步：新增 128 条元数据」）

**前端**：一个「同步」面板 —— 显示设备、上次同步时间与结果、一个「立即同步」按钮、
以及配对用的二维码 / 密钥输入框。

## 五、分三段做

| 阶段 | 内容 | 说明 |
| --- | --- | --- |
| **一** | 共享密钥配对 + 手动填 IP + 一次请求双向同步 | 主体。**先把「合并规则」写全并单测透** —— 传输随时能换，规则错了数据就脏了 |
| 二 | UDP 广播自动发现 | 手机自动列出「发现的设备」，找不到再退回手填 |
| 三 | 连上家里的 Wi-Fi 自动同步一次 | 应用回到前台时补一次，配合已有的保活前台服务 |

> 也可以先做一个**更省事的前置**：把同样的载荷导出成一个 `.json` 同步包，走微信/USB 传。
> 网络层一行不写，就能把「合并规则」在真实数据上验通 —— 那部分代码**后面完全复用**。

## 六、跨网怎么办（不在同一个 Wi-Fi）

**不要自己造。** 建议直接用 **Tailscale / ZeroTier** 这类组网工具：装完之后两台设备在系统
层面就「永远在同一个局域网」，同步代码**一行都不用改**，连 UDP 广播都能穿过去。

自己做 NAT 穿透 + 中转是另一个量级的工程，而且做不好就是一个安全漏洞。

## 七、风险与已知坑

| 风险 | 说明与对策 |
| --- | --- |
| **手机端的 pid 覆盖率没量过** | 电脑是 98.6%，手机未知。**如果手机没回填过 pid，收藏就没法按 pid 匹配** —— 开工前必须先量 |
| **路由器开了 AP 隔离** | 客用 Wi-Fi / 部分路由器会拦客户端之间的一切流量，广播和直连都不通。对策：回退手填 + 明确报错，别只说「没找到设备」 |
| **Android 省电会杀前台** | 同步要跑到几百毫秒到几秒，用已有的保活前台服务包住（元数据补全已经在用同一套） |
| **时钟偏差** | 见 3.5：秒级 + 设备 id 定序，不用墙钟单独裁决 |
| **两端 schema 版本不同** | 同步协议要带 `schema_version`，落后的一方先自己迁移；差太远就拒绝并提示升级 |
| **误删传播** | 「移除作品」会进忽略名单并同步出去。要留一个「本次不同步忽略名单」的开关，免得误操作扩散到两台设备 |

## 八、还没定的两件事

1. **收藏冲突用哪种规则**：本文默认「后来者赢」（3.4 / 3.5）。备选是「并集（只增不减）」
   和「一端说了算」，各有明显缺点，见之前的讨论。
2. **要不要先做「同步包」那一版**：半天能做完，能把合并规则先验通，代价是每次手动搬一次文件。
